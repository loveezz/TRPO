Условные обозначения: [В] — ошибка ввода, [О] — ошибка обработки данных.

| № | Место (файл:функция) | Тип | Ошибка (до исправления) | Симптом: «неверный, но правдоподобный результат» |
|---|----------------------|-----|--------------------------|---------------------------------------------------|
| 1 | `handlers.go: toInt/toUint/toFloat` (бывшие, удалены) | [В] | `n, _ := strconv.Atoi(...)` — ошибка разбора игнорировалась | `age="abc"` → `0`; `salary="abc"` → `0` (проходит `Salary>=0`); `experience="NaN"` → `NaN`; фильтр `age_min="abc"` → `0` (фильтр молча не применяется); `id="abc"` → `0` (смешение 400 и 404) |

| 3 | `handlers.go: validateCandidate` (старый) | [В][О] | Только `!= ""`, `Age>0`, `Exp>=0`, `Salary>=0`; одно общее сообщение | Пропускал: `age=999`, `email="not-an-email"`, `phone="abc"`, `experience=1000`, `salary=999999999`; возраст `0` от `toInt("abc")` давал ложный 400 без указания поля |
| 4 | `handlers.go: validateVacancy` (старый) | [В][О] | Без диапазонов, без белого списка занятости, общее сообщение | Пропускал инверсию `salary_max < salary_min` при `min=0`? частично ловил, но без деталей; пропускал `min_exp=1000`, `employment="XXX"` |

| 7 | `handlers.go: Login` | [В] | Нет проверки пустых полей и формата email | Пустой запрос уходит в БД (`LOWER(email)=LOWER('')`); мусорный email без диагностики |

## 6.3 Описание локальных проверок результатов операций, вызовов функций, с печатью текущих переменных

Принцип (п. 5.1): каждая проверка входа/выхода печатает отвергнутое значение + контекст.
Уровень: `[WARN]` — ошибка ввода (исправлена/отклонена без падения), `[ERROR]` — внутренняя ошибка БД.

**1. Разбор чисел фильтра — терпимый (фильтр не должен падать):**
`handlers.go: parseFilterInt / parseFilterFloat`
```go
v, present, err := service.ParseOptionalInt(raw)
if err != nil {
    log.Printf("[WARN] фильтр %s=%q некорректен (%v), значение проигнорировано", field, raw, err)
    return 0
}
```
Пример лога: `[WARN] фильтр age_min="abc" некорректен (ожидалось целое число...), значение проигнорировано`.

**2. Разбор `:id` — строгий:**
`handlers.go: parseID` + `service.ParseID`
```go
id, err := service.ParseID(c.Params("id"))
if err != nil {
    log.Printf("[WARN] некорректный id в %s: raw=%q err=%v", c.Path(), c.Params("id"), err)
    return 0, err
}
```
Мусор → 400 + печать `raw`, а не молчаливый `0` → 404.

**3. Разбор обязательных полей формы — строгий:**
`service.MustInt / MustFloat` различают `""` («не заполнено») и `"abc"` («ожидалось число, получено "abc"»);
отклоняют `NaN/Inf` (т.к. `ParseFloat("NaN")` успешен, но ломает сравнения).
В `CreateCandidate/UpdateCandidate` печатаются все ключевые переменные:
```go
log.Printf("[WARN] CreateCandidate: %v (full_name=%q age=%q email=%q)", err, ...)
log.Printf("[WARN] CreateCandidate validate: %v (candidate=%+v)", err, candidate)
```

**4. Проверки репозитория:**
`repository.go: SearchCandidates` — печать + исправление на месте:
```go
log.Printf("[WARN] SearchCandidates: age_min=%d > age_max=%d, границы переставлены", ageMin, ageMax)
log.Printf("[WARN] SearchCandidates: gender=%q не из белого списка, фильтр проигнорирован", f.Gender)
log.Printf("[WARN] SearchCandidates: experience_min=%v < 0, фильтр проигнорирован", f.ExperienceMin)
```

**5. Проверки сортировки:**
`handlers.go: Candidates` + `service.NormalizeSort/IsValidSort`:
```go
if raw := c.Query("sort", ...); !service.IsValidSort(raw) { log.Printf("[WARN] Candidates: sort=%q неизвестна, ...", raw) }
```
Неизвестное значение приводится к `experience` детерминированно.

**6. Скрытие внутренних ошибок:**
`handlers.go: internalError`
```go
log.Printf("[ERROR] %s: %v", where, err)
return fiber.ErrInternalServerError
```
Клиент получает generic 500, инженер — полный контекст (`SaveCandidate`, `SearchCandidates`, ...).

**7. Проверки конфигурации и сессий:**
`config.go: Load` печатает `APP_PORT=%q некорректен`, `DATABASE_DSN пуст/не задана`, `SESSION_SECRET по умолчанию`;
`session.go: Verify` явно отклоняет `id == 0`.

**Проверка работы (выполнено):**
```bash
go vet ./...        # чисто
go test ./...       # ok (11 тестов, включая граничные)
go build ./...      # BUILD-OK
go test ./internal/service/ -v  # все PASS
```

## 6.4 Способы проверки входных и выходных данных на их корректность

Все способы — из `internal/service/validation.go` (единая точка защитного программирования):

**Входные данные (формы, query, URL, env):**

1. **Различение «отсутствует» vs «мусор»:** `ParseOptionalInt/Float` → `(val, present, err)`.
   Фильтр: пусто = «критерий не задан», мусор = WARN + игнорировать.
   Форма: `MustInt/MustFloat` — пусто и мусор = 400 с именем поля.
2. **Белые списки:** `IsAllowedGender` (`Мужской|Женский`), `IsAllowedEmploymentType`
   (3 значения), `NormalizeSort/IsValidSort` (4 значения). Всё остальное — WARN + игнорирование/400.
3. **Диапазоны:** возраст `14..100`, опыт `0..60`, зарплата `0..10000000`, длины
   (ФИО 2..200, город 2..120, навык ≤100, навыков ≤30, about ≤5000). `NaN/Inf` отклоняются явно.
4. **Форматы:** `ValidateEmail` (`net/mail.ParseAddress` + зона + без пробелов + ≤254),
   `ValidatePhone` (6..32 символа, ≥6 цифр, только `+ - space ( ) .`).
5. **Нормализация:** `TrimSpace` всех строк до проверки и до SQL; `EscapeLike` для `% _ \`
   + `ILIKE ... ESCAPE '\'` в `repository.go` — ввод `%` ищет буквальный `%`, а не «всё».
6. **Перекрёстные соотношения:** `ValidateVacancy`: `salary_max >= salary_min`;
   `SearchCandidates`: `age_min > age_max` → перестановка с WARN.
7. **Идентификаторы и конфиг:** `ParseID` (>0); `config.Load`: порт `1..65535`, DSN непустой,
   WARN о дефолтном секрете; `session.Verify`: `id != 0`.

**Выходные данные (скоринг, отображение, ответы):**

1. **Нормализация перед сравнением:** `ScoreCandidate` триммит город/занятость/образование;
   пустые `city/employment` баллов не дают (устранены фантомные +5+5); образование:
   `eduV==""` → +5, иначе нужно непустое `eduC` с `Contains`.
2. **Санитизация чисел:** `NaN/Inf/отриц. опыт` → `0`; отрицательная зарплата баллов не даёт
   (раньше `-1 <= max` давало +10); итог ограничен `0..100`.
3. **Форматирование:** `formatSalary` выносит знак перед группировкой (`-1 000 000`);
   отрицательная зарплата из повреждённых данных отображается корректно.
4. **Сокрытие внутренностей:** любая ошибка `Repo.*` → `log [ERROR]` + generic 500,
   сырые тексты Postgres наружу не уходят. Успешные пути возвращают только проверенные структуры.

## 6.5 Ответы на контрольные вопросы (кратко, подробно — в разделе 7)

- **7.1** Суть ЗП — презумпция враждебных входов: проверять входы/выходы модуля по спецификации и явно обрабатывать нарушение вместо возврата правдоподобной лжи.
- **7.2** Рационально — на границах доверия (формы, query, URL, env, БД-строки, скоринговые формулы); нерационально — в горячих внутренних циклах с доказанными инвариантами.
- **7.3** Нет — ЗП локально (проверки вызовов/печать переменных), а не глобально (архитектура, структуры, ООП). Без базовой методологии проверять нечего.
- **7.4** Обнаружение: строгий разбор без `_`, белые списки, диапазоны, `EscapeLike`, `go vet` + тесты границ; локализация: детализированная ошибка с именем поля + `log` отвергнутого значения + контекст (`candidate=%+v`, `filter=...`), разделение 400 (ввод) / 404 (нет записи) / 500 (внутр.).

## 7. Контрольные вопросы (полные ответы)

**7.1 В чём суть защитного программирования?**
Исходная предпосылка (п. 5.1): худшее, что может сделать модуль, — принять неправильные
входные данные и вернуть неверный, но правдоподобный результат. Поэтому в текст модуля
включают проверки входов/выходов на соответствие спецификации (ограничения на поля и
соотношения между ними). При нарушении возбуждается исключительная ситуация, а в конце
модуля — её обработчики: диагностика + либо исправление данных, либо ослабление влияния
ошибки. В узком смысле — локальные приёмы: проверка результатов операций и вызовов,
печать текущих переменных. В проекте: `MustInt("abc")` → 400 `поле "возраст": ожидалось
целое число, получено "abc"` вместо молчаливого `0`; `EscapeLike("%")` → поиск буквального
`%` вместо «выбрать всё»; `ScoreCandidate` не начисляет баллы за `"" == ""`.

**7.2 В каких случаях рационально его применять?**
Когда цена правдоподобной лжи выше цены проверок: границы доверия (наш случай —
HTML-формы, query-фильтры, `:id`, env, строки из БД, формула скоринга), ненадёжные
источники, критичные решения (зарплатная вилка, подбор). Нерационально — в доказанно
корректных внутренних инвариантах и горячих путях, где проверки дублируют гарантии типов
(п. 5.1 прямо требует регулировать степень ЗП по спецификации качества: время/память
против надёжности). В проекте проверки сосредоточены на `handlers` + `repository` +
`ScoreCandidate`, а не в `sort.SliceStable` или `joinSkillNames`.

**7.3 Можно ли создать программный продукт только с помощью защитного программирования?**
Нет. ЗП — не глобальная методология (в отличие от структурного/ОО-подхода), а набор
локальных проверок (п. 5.1). Оно не задаёт декомпозицию, модели данных, контракты слоёв.
Без базовой архитектуры проверять нечего: белый список `employment_type` бессмыслен без
моделей `Candidate/Vacancy` и слоёв `handlers → repository → service`. В проекте ЗП
добавлено поверх готового продукта ПР № 1–3, а не вместо него.

**7.4 Каким образом можно осуществить обнаружение и локализацию ошибок ввода и обработки данных?**
*Обнаружение:* (а) контроль времени компиляции — `go vet`, строгая типизация, запрет `_, _ :=`
на разборе; (б) условная компиляция/флаги для диагностических сборок; (в) защитные проверки:
строгий разбор (`ParseID/MustInt/MustFloat`), белые списки, диапазоны, форматы
(`ValidateEmail/ValidatePhone`), экранирование (`EscapeLike`), перекрёстные проверки
(`salary_max>=salary_min`, `age_min<=age_max`), тесты границ (`validation_test.go`:
`999`, `NaN`, `%_`, `""==""`, `-1000`).
*Локализация:* детализированная ошибка с именем поля и отвергнутым значением
(`поле "возраст": ... получено "abc"`), печать текущих переменных
(`log [WARN] фильтр age_min="abc"...`, `candidate=%+v`), разделение кодов
(400 — ввод, 404 — нет записи, 500 — внутренняя с `[ERROR] <место>: <err>` без утечки деталей),
воспроизводимые тесты на каждый дефект. Именно так в проекте локализованы все 19 точек из §6.2.
